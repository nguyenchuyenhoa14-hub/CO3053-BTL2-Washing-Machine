\section{Test Plan}
\label{sec:testplan}
% =============================================================================

\subsection{Strategy}

The test cases were written \emph{before} running them and are executed at two levels:

\begin{enumerate}
  \item \textbf{Automated host tests (PC).} The exact same FSM, debounce, blinker and gesture code is
        compiled with \code{gcc} and driven by event sequences. A mock HAL records every output
        (LED modes, motor, pump, door lock, returned coins). Time is simulated, so a 30-minute cycle is
        tested in milliseconds and boundary times (e.g.\ 1499\,ms vs 1501\,ms) are exact.
        Command: \code{make test test_hal test_gesture test_two_button test_ui_text}.
  \item \textbf{Hardware tests (board).} The firmware is flashed on the WeAct STM32H750 and each scenario
        is performed with K1 (or the UART keys). The LCD, the PE3 LED and the UART log are observed and
        recorded (board photos and the demo video, Section~\ref{sec:results}).
\end{enumerate}

\noindent Requirement coverage: every functional requirement FR-01\dots FR-11 and every assumption
A1\dots A10 is checked by at least one test case below; every transition T01\dots T22 is exercised by the
automated suite.

\noindent\textit{Note on TC04 on the board.} With the single-key front panel the coins are staged and
confirmed by a 1.2\,s hold (Section~\ref{sec:hardware}); confirming with $<50$\cent{} is the board
equivalent of pressing RUN without enough money. The FSM behaviour itself (RUN ignored in COLLECTING) is
verified by automated test TC-05.
